# Переключение между двумя серверами odora

Схема для двух серверов с физической репликацией PostgreSQL (`deploy/replication` в репозитории odora):

```text
              Пользователи → odora.uz
                      │
              Cloudflare Worker            не стоит ни на одном из серверов
              │  каждые 5 с: GET /_edge/health
     ┌────────▼────────┐   ┌─────────────────┐
     │ origin-1        │   │ origin-2        │
     │ агент  ✔ готов  │   │ агент ✘ реплика │
     │ odora           │   │ odora (ждёт)    │
     │ БД: основная    │──▶│ БД: копия       │
     └─────────────────┘   └─────────────────┘
```

## Как это работает

- **Агент на каждом сервере** отвечает на `GET /_edge/health` кодом 200, только если приложение рядом отвечает **и** локальная база — основная и принимает запись. Иначе 503 с причиной (`database_is_replica`, `app_unavailable`, …).
- **Worker** опрашивает оба сервера и ведёт трафик на готовый. Сервер, чей агент сам говорит «не готов», не используется никогда, даже если больше идти некуда: лучше 503, чем приложение на базе «только чтение».
- **Odora на каждом сервере работает только со своей локальной базой.** На резервном сервере backend при старте видит, что база — реплика, не запускает миграции и фоновые задачи и ждёт её повышения, отвечая на `/health` кодом 503 (`"status":"standby"`). После повышения он сам применяет миграции и начинает работать.
- **Переключение — одно действие:** повысить базу на резервном сервере (панель агента → PostgreSQL → «Повысить до primary»). После этого приложение там стартует, health становится 200, Worker сам переводит трафик. Ничего перенастраивать не нужно.
- **Защита от возврата старого сервера.** После повышения база получает следующий номер поколения (timeline PostgreSQL). Две независимые защиты не дают трафику вернуться на сервер со старыми данными:
  1. Агент старого сервера спрашивает соседа. Увидев там основную базу более нового поколения, он отвечает `fenced_old_primary` и запоминает это на диске (`fence.json` рядом с конфигурацией), так что перезапуск и последующая недоступность соседа ничего не меняют.
  2. Worker помнит наибольшее поколение, которое видел, и не ведёт трафик на сервер с меньшим, каким бы ни был его приоритет.
- **WebSocket** (звонки) Worker передаёт тому же серверу, что и обычные запросы.

## Что произойдёт при сбоях

| Событие | Результат |
|---|---|
| Упало приложение на основном, база жива | 503 до восстановления приложения: резервный сервер не может писать в свою базу |
| Основной сервер пропал целиком | 503, пока вы не повысите базу на резервном; затем трафик идёт туда сам |
| Старый основной вернулся | Трафик остаётся на новом; в панели старого — «Устаревший primary». Его базу нужно пересоздать как реплику (`replica-setup.sh`) |
| Пропала связь между серверами, оба живы | Ничего не меняется: резервный остаётся репликой, автоматического повышения нет |
| Недоступен Cloudflare | Сайт недоступен; серверы и данные не затронуты |

Повышение базы делает человек. Автоматика здесь опасна, пока наблюдатель один: обрыв связи между серверами выглядит как авария и дал бы две основные базы.

## Настройка

### 1. Агент на каждом сервере

Установка — как в [DEPLOY.md](DEPLOY.md) (Docker Compose). Конфигурация — по образцу [`deploy/failover/agent-config.odora_1.example.json`](deploy/failover/agent-config.odora_1.example.json); на втором сервере в разделе `node` меняются `database` на `odora_2` и адрес соседа на `origin-1`. Раздел `node`:

```json
"node": {
  "appHealthUrl": "http://host.docker.internal:3001/health",
  "database": "odora_1",
  "peers": ["https://origin-2.odora.uz/_edge/health"]
}
```

В `agent.env`: `PGUSER`/`PGPASSWORD` (роль с `pg_monitor`) для проверки роли базы; `PG_ADMIN_USER`/`PG_ADMIN_PASSWORD` — чтобы повышать базу из панели. Порт backend-а у серверов может отличаться (3001 или 3002) — проверьте `appHealthUrl` и `origins`.

### 2. nginx на каждом сервере

В блок `origin-N.odora.uz` добавьте [`deploy/failover/nginx-edge-health.conf`](deploy/failover/nginx-edge-health.conf), затем `nginx -t && systemctl reload nginx`. Проверка:

```bash
curl -s https://origin-1.odora.uz/_edge/health    # {"ready":true, …, "db":{"role":"primary","timeline":1}}
curl -s https://origin-2.odora.uz/_edge/health    # {"ready":false,"reason":"database_is_replica", …}  (код 503)
```

### 3. Worker

```bash
npx wrangler login
npx wrangler secret put APP_CONFIG      # вставьте содержимое deploy/failover/worker-config.example.json одной строкой
npx wrangler deploy
```

`"publicAccess": true` означает, что вход остаётся на стороне odora, Worker только маршрутизирует. Сначала проверьте Worker на его адресе `*.workers.dev`, и только потом привязывайте к `odora.uz` (Cloudflare → Workers → Settings → Domains & Routes → Route `odora.uz/*`); для этого домен должен обслуживаться Cloudflare.

Изменение списка серверов — это новое значение `APP_CONFIG` (`wrangler secret put`), применяется без повторной выкладки.

### 4. После привязки домена

- Закройте порты 80/443 на серверах для всех, кроме [адресов Cloudflare](https://www.cloudflare.com/ips/) и адреса соседнего сервера: иначе Worker можно обойти.
- Redis и файлы (`storage`) PostgreSQL не реплицирует: без их синхронизации на резервном сервере после переключения не будет описаний коллекций и вложений.
- Секреты JWT в `.env.prod` на обоих серверах должны совпадать, иначе пользователи разлогинятся при переключении.

## Учебное переключение

Проведите его до настоящей аварии, в тихое время:

1. Остановите odora и PostgreSQL на основном сервере (`docker stop …`). Сайт начнёт отвечать 503.
2. В панели агента резервного сервера: PostgreSQL → «Повысить до primary».
3. Через 10–20 секунд сайт должен открыться; `curl -s https://origin-2.odora.uz/_edge/health` покажет `"timeline": 2`.
4. Запустите прежний основной. Его агент должен ответить `fenced_old_primary`, сайт — остаться на новом сервере.
5. Пересоздайте прежний основной как реплику нового: `primary-setup.sh` на новом основном (с `REPLICA_NAME=odora_1`), `replica-setup.sh` на прежнем.

## Что проверено

`npm test` (43 теста) и локальный запуск Worker в `wrangler dev` против двух тестовых серверов: обычная работа, 503 при недоступном основном и реплике на резервном, переход после повышения, отказ возвращаться на старый сервер, WebSocket в обе стороны на каждом шаге. В Cloudflare и на боевых серверах схема не запускалась.
